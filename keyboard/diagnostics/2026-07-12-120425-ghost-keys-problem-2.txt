  The ghosting pattern

  Every broken key maps to (row, col0-or-1), and the "extra" key is always the
  next row in the row_pins tuple order, same column:

  ┌─────────────┬────────────────┬────────────┬────────────┐
  │ Key pressed │ row_pins index │ Extra key  │ next index │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ F3          │ row 2          │ Next(PgDn) │ row 3      │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ Next(PgDn)  │ row 3          │ F5         │ row 4      │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ F5          │ row 4          │ F7         │ row 5      │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ F7          │ row 5          │ F9         │ row 6      │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ F8          │ row 5, col 1   │ F10        │ row 6      │
  ├─────────────┼────────────────┼────────────┼────────────┤
  │ F9          │ row 6          │ END        │ row 7      │
  └─────────────┴────────────────┴────────────┴────────────┘

  That's a continuous chain, rows 2→3→4→5→6→7, in exactly the order the rows
  appear in code.py:17-20 (GP13, GP14, GP20, GP15, GP22, GP21). Rows 0/1
  (F1/F2/F11/F12) aren't affected, and it doesn't wrap row 7→row 0. This is a
  textbook "adjacent row leaks into the next-scanned row" ghost — when row R is
  driven and a key is pressed, row R's line doesn't fully drop before row R+1 is
  driven, so the same column reads HIGH again on row R+1's scan. Since it only
  shows up on columns 0/1 (the F-key column) so far, either those column traces
  have more capacitance/length, or you simply haven't tested other columns on
  rows 2-7 yet (worth checking, e.g. does TAB/W ghost into Q/E?).

  This pattern could come from either side:
  - Hardware: a physical short/crosstalk between adjacent row conductors — bad
  solder joint, frayed ribbon, oxidized/misaligned connector pins — spanning
  that contiguous run of rows.
  - Software/electrical timing: CircuitPython's native keypad.KeyMatrix (the
  actual scan loop lives in C, not in this repo) not leaving enough settle time
  before switching rows, combined with column trace capacitance.

  Tests to tell them apart

  1. Enable KMK debug and watch raw scan coordinates. Set
  Debug(__name__).enabled = True in code.py:10, open the serial console, press
  just F3. If you see two distinct (row, col) events fire (r2,c0) and (r3,c0),
  the ghost is happening at the electrical/matrix level — hardware. If only one
  matrix position is scanned but two HID codes go out, it'd be a firmware bug
  (unlikely — I checked the keymap, each position maps to exactly one key).
  2. Multimeter continuity check (Pico powered off, nothing pressed): measure
  resistance between the suspect row pins/wires (e.g. between the wire going to
  GP13 and the wire going to GP14, at the ribbon connector). Near-0Ω where there
  shouldn't be any connection = confirmed hardware short.
  3. Re-order test: temporarily swap two of the affected rows' positions in the
  row_pins tuple (keeping the same physical wire-to-GPIO connections, just
  changing scan order) and update the keymap rows to match. If the ghost still
  follows the same physical wires (e.g. GP13 still leaks into GP14 regardless of
  scan order), that confirms a physical short rather than a scan-order
  artifact.

⏺ That log confirms the ghost is happening at the raw matrix-scan level, not in
  firmware — two genuinely separate key_number events (22 and 33) fire from one
  press of F3. So it's hardware. But the timing rules out a simple wire-to-wire
  short, and points somewhere more specific:

  - key_number 33 (Next) fires 42–72ms after key_number 22 (F3), not in the same
  scan cycle. A hard short between the row lines would assert both almost
  instantly (within one ~2ms scan). This lag looks like something taking time to
  make contact.
  - The release order flips between attempts — 22-then-33 released in trial 1,
  but 33-then-22 in trials 2 and 3. A fixed electrical short would behave
  consistently; this doesn't.

  That pattern — delayed, inconsistent, tied to a specific pair of keys that are
  physically adjacent on the keyboard (F3 sits right above Next/PgDn in that
  vertical F-key column) — is much more characteristic of a worn or cracked 
  membrane/flex-circuit trace than a wiring short. On old membrane keyboards
  like this one, pressing a key can slightly deform the membrane; if there's a
  crack or worn conductive trace near the boundary between two adjacent key
  pads, that flex can momentarily bridge into the neighbor's contact — with
  exactly this kind of soft, variable-delay, order-inconsistent behavior. It
  would also explain why your multimeter check (at rest, unpressed) found
  nothing: the bridging only happens under the mechanical pressure of an actual
  keypress, not when the keyboard is idle.

  Since the whole chain (F3→Next→F5→F7→F9→End) runs down that same physical
  column, this suggests wear or damage along that entire strip of the membrane,
  not just one spot.

  Two follow-ups worth doing:
  1. Continuity test while pressed: hold F3 down and check for continuity
  between the row2/row3 conductors (or right at the keyboard's ribbon connector
  pins) while pressed — a short that only appears under pressure would confirm
  the membrane-crack theory directly.
  2. Visual inspection: if the keyboard can be opened, look at the membrane/flex
  circuit in the F3–End column for visible cracks, worn silver-ink traces, or
  debris between adjacent pads.

❯ the keyboard has diodes for each key, can this explain uni-directionality?    
  could it be a faulty diode?                                                   

⏺ Good instinct to check, but the per-key diode is probably not the mechanism
  here — the topology doesn't quite support it.

  Each key's diode sits in series with its own mechanical switch contact. For F3
  (row2, col0), current only flows through F3's diode if F3's own switch is
  physically closed. Row2 being driven HIGH (which happens every scan cycle,
  whether or not F4 is pressed) forward-biases every diode in that row — but a
  forward-biased diode with an open switch in series still blocks current. So
  even a completely dead-shorted F3 diode wouldn't explain col0 going HIGH only
  when F4 is pressed and F3 is untouched — a shorted F3 diode would instead make
  F3 register on every single row2 scan, constantly, regardless of F4, since
  row2 gets driven HIGH continuously during normal scanning. That's not what
  you're seeing (F3 behaves normally except when F4 happens to trigger it).

  Similarly, a leaky/reverse-conducting F4 diode would only let current bleed
  backward from col1 into row2 — it doesn't create a path from col1 to col0,
  since those are two separate column wires with no diode connecting them to
  each other.

  For col0 to go HIGH purely because col1 went HIGH, you need a direct
  electrical path between the col0 and col1 traces themselves, bypassing both
  switches and both diodes — i.e., a physical bridge on the PCB/membrane
  specifically near row2 (and separately near row1 for F11/F12). That fits
  everything you've measured: it's row-specific (only where the bridge
  physically exists), independent of the keys' own diodes, and explains why F3
  alone doesn't misfire on every scan.

  The one-directionality is still explainable without invoking a broken
  intentional diode: corrosion or oxide bridges between two copper traces/pads
  don't always behave like a clean resistor — oxide layers between two metal
  surfaces can form an accidental rectifying junction (sometimes called the
  "rusty bolt effect"), conducting much better in one direction than the other.
  A stray solder whisker or conductive debris flake anchored on the col1 side,
  flexing onto the col0 pad only when that specific key is pressed, would
  produce the same asymmetric result mechanically, no oxide chemistry required.

  If you want to test this directly: use your multimeter's diode-test mode (not
  just continuity) between the col0 and col1 traces near row2, in both
  polarities. If you get a low reading one way and open/very-high the other way,
  that's a real rectifying bridge between the columns — strong confirmation of
  an unintended short/corrosion junction rather than a failed keyboard diode.

⏺ Good question to nail down before you start probing — here's the precise
  procedure.

  Meter mode: diode-test mode, not just the beep/continuity mode.
  Continuity mode only tells you "below some threshold resistance, beep" —
  usually a few tens of ohms — and hides the actual number. Diode-test mode
  pushes a small current through the probes and shows you a voltage, which lets
  you distinguish three very different situations instead of just pass/fail:

  - ~0.00–0.05V → a dead short (near-zero resistance) — a proper bridge, e.g.
  tin/solder or debris directly connecting the two pins.
  - A stable diode-like drop, roughly 0.3–0.7V in one direction, OL (open) the 
  other way → a rectifying junction — this is the "corrosion acting like an
  accidental diode" scenario I mentioned earlier. Note it doesn't have to hit
  the textbook silicon 0.6V exactly; corrosion junctions are messier. Any non-OL
  reading in only one direction counts.
  - OL both directions but the reading flickers/jumps toward a value while 
  you're flexing → a marginal, contact-dependent leak — not a hard short at all,
  just barely-touching material that makes and breaks contact with movement.
  This matches the timing behavior you've already seen (10-70ms lag,
  inconsistent release order), so this is honestly the outcome I'd bet on.

  Before you touch anything: unplug the Pico from USB. With it powered and
  running, the GPIO pins are actively driven/pulled by the microcontroller, and
  the meter's tiny test current will be fighting that — you'll get confusing,
  unstable readings that don't reflect the connector itself. You want both lines
  fully floating.

  Polarity: test both directions, as two separate readings.
  1. Red probe on pin 20 (row5/F7), black probe on pin 21 (row6/F9). Note the
  reading.
  2. Swap: red on 21, black on 20. Note the reading.

  Do the same for pins 1 and 2. The reason to check both: since we found the
  F4→F3 and F12→F11 ghosts only ever go one direction (never the reverse), if
  there's a real asymmetric junction at pins 1/2, you'd expect the diode-mode
  reading to differ noticeably between the two polarities — confirming that
  asymmetry electrically rather than just behaviorally.

  What "normal/healthy" looks like, so you know what you're comparing against:
  at rest, with no keys pressed, there is no legitimate electrical path between
  two row lines (or two column lines) at all — every real path in this matrix
  goes row→diode→column through an actual keypress. So on a healthy pair, you
  should get OL in both directions, full stop. Any reading at all — short,
  diode-like, or a flickery near-open — is abnormal and is your evidence.

  The flex test: hold both probes steady on the two pins (resting them so they
  don't slip is easier than trying to hold pressure the whole time — alligator
  clips or a helping hand are useful here), watch the display, and with your
  other hand gently bow/wiggle the ribbon cable right where it enters the
  connector, and separately try pressing on the connector body itself. You're
  watching for the reading to jump from OL to something during the flex — that's
  the moment you've caught it in the act. If your meter has a MIN/MAX-hold or a
  peak-capture mode, use it, since a brief flex-induced blip can be easy to
  miss on a normal 2-3-reading-per-second display.

  One practical caution: if this is a fine-pitch FFC connector, don't jam meter
  probes into the housing — you risk bending or spreading the tiny contacts.
  Probe at the PCB-side solder pads for those pins instead (same net, easier and
  safer to reach), and use needle-tip probes if you have them so you don't
  accidentally bridge two adjacent pads yourself with a fat probe tip and
  produce a false short.

❯ in diode does current flow from cathode to anode? Meaning if I apply + to     
  cathod and - to anode will current flow?                                      

⏺ No — it's the opposite. Current flows anode → cathode through a diode when
  forward biased (anode more positive than cathode). If you put + on the cathode
  and − on the anode, that's reverse bias, and a healthy diode blocks it —
  you'd read OL ("1.") on the meter, not a voltage drop.

  So on your multimeter in diode-test mode: the red probe is the internal +
  source, black is −.
  - Red on anode, black on cathode → forward bias → meter shows a voltage drop
  (typically ~0.4–0.7V for silicon, sometimes lower for germanium/Schottky) —
  this confirms the diode is good and oriented that way.
  - Red on cathode, black on anode → reverse bias → meter shows OL — also
  expected/good, confirms the diode isn't leaking backward.

  One thing worth knowing for this specific keyboard if you ever want to test
  one of the actual per-key diodes (not the row-to-row connector test we've been
  doing): the README notes this matrix uses columns_to_anodes=False, meaning
  it's wired opposite to the usual convention — the row lines are the anodes, 
  and the column lines are the cathodes. So to check a healthy individual key's
  diode, you'd hold that key physically pressed (to close the switch and
  complete the path) and put red on that key's row pin, black on its column pin,
  and expect a forward drop; swapped, you should get OL.
